# Review of v0.5.0 before WMS completion (2026-11-10)

Owning module: architecture/security. Scope: everything delivered in v0.5.0 plus the CI fixes of
2026-11-09. Method: code read-through of every WMS service, the auth/authz stack and the
migrations; comparison with the original specification §3–§9 and with `NEXT_TASKS.md`; results
of the first real GitHub Actions run. Findings are numbered **R-xx** and tracked in
`docs/WMS_RELEASE_GATE.md`.

The v0.6 continuation prompt and production-readiness checklist referenced by the product owner
were **not available** when this review was written; the checklist used is derived from the
original specification and must be re-mapped when those documents arrive.

## 1. Functional gaps in the WMS

| Id   | Finding                                                                                                                                                                                                                                         | Impact               | Severity |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- | -------- |
| R-01 | No command releases QUARANTINE / DAMAGED / INSPECTION stock back to AVAILABLE (or scraps it with a status-aware reason). Returned units sent to quarantine can never become saleable except through an audited adjustment pair (lossy history). | Operational dead end | High     |
| R-02 | `sku_barcodes.qty_per_uom` is stored but never applied: scanning a box barcode (e.g. 10 units) during receiving, picking or packing counts the typed quantity in base units.                                                                    | Wrong quantities     | High     |
| R-03 | Transfers drop lot codes (TRANSFER_IN always uses lot `''`), breaking lot traceability across warehouses.                                                                                                                                       | Traceability         | Medium   |
| R-04 | No "unpick": picked stock in the packing area cannot be returned to a shelf, and `close` refuses orders with picked-but-undispatched stock ⇒ such orders can get stuck.                                                                         | Operational dead end | High     |
| R-05 | Movable containers cannot be closed/retired; storage nodes cannot be renamed or deactivated (only created).                                                                                                                                     | Topology maintenance | Medium   |
| R-06 | A DRAFT transfer can only be cancelled through the destination's `close`; the source side has no cancel.                                                                                                                                        | Workflow             | Low      |
| R-07 | Lot-tracked SKUs: allocation is lot-agnostic (no FEFO/FIFO, no lot selection); serial uniqueness not enforced.                                                                                                                                  | Traceability         | Medium   |
| R-08 | No transfer-side reservation: a source dispatch competes with outbound allocations only through free-quantity checks (safe, but no planning).                                                                                                   | Planning             | Low      |
| R-09 | Activity history cannot be exported; no cross-document search.                                                                                                                                                                                  | Reporting            | Low      |
| R-10 | Outbound packages created on a cancelled order remain ACTIVE (empty).                                                                                                                                                                           | Data hygiene         | Low      |

## 2. Security findings

| Id   | Finding                                                                                                                                                                           | Severity |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| R-11 | No phishing-resistant MFA (WebAuthn/passkeys); admins rely on TOTP (SEC-OPEN-001).                                                                                                | High     |
| R-12 | Users cannot change their own password while logged in (ASVS V6 requirement); only admin-issued reset exists.                                                                     | Medium   |
| R-13 | Users cannot list or revoke their own active sessions; no "log out other devices".                                                                                                | Medium   |
| R-14 | Recovery codes cannot be regenerated by the user (only via MFA reset by an admin).                                                                                                | Low      |
| R-15 | `command_log`, expired sessions, used one-time tokens and published outbox rows are never purged (unbounded growth; stale personal metadata such as IPs/user agents in sessions). | Medium   |
| R-16 | Module boundaries are convention-only; nothing stops future code from writing stock tables directly.                                                                              | Medium   |
| R-17 | The idempotency conflict message reveals that _another_ user used a key (low-value oracle).                                                                                       | Low      |
| R-18 | Admin-only routes are guarded per service method but there is no automated test enumerating every route for authorization (a new route could ship unguarded).                     | Medium   |

No injection, IDOR or tenant-isolation defect was found; existing negative tests cover them.
